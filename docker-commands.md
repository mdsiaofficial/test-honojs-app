# 🏗️ PART 1: The Build Command

### `docker build -t test-honojs-app .`
*(Engineer 1 & 2 use this exact structure, just with different names)*

| Component | What it is | Detailed Explanation |
| :--- | :--- | :--- |
| `docker` | The CLI Program | This invokes the Docker Command Line Interface. It tells your computer, "I am about to give a command to the Docker engine." |
| `build` | The Subcommand | This tells Docker you want to **create a new image** by reading instructions from a `Dockerfile`. |
| `-t` | The Flag (Tag) | Short for `--tag`. It assigns a human-readable name (and optionally a version, like `my-app:v1`) to the image being built. Without this, Docker gives the image a random, unreadable ID (like `a3f8b9c2d1e4`). |
| `test-honojs-app` | The Image Name | The actual name you are giving your image. You can use this name later to run the container. |
| `.` | The Build Context | **Crucial.** The dot means "the current directory". Docker needs a "context" (a folder) to look for the `Dockerfile` and any files mentioned in `COPY` commands inside the Dockerfile. It sends this entire folder to the Docker engine to build the image. |

# 🚀 PART 2: The Run Command

### `docker run -d --name test-honojs-app -p 5000:5000 test-honojs-app`

| Component | What it is | Detailed Explanation |
| :--- | :--- | :--- |
| `docker` | The CLI Program | Invokes the Docker engine. |
| `run` | The Subcommand | This is a two-in-one command. It does **`docker create`** (makes a container from an image) AND **`docker start`** (turns it on) in a single step. |
| `-d` | The Flag (Detach) | Short for `--detach`. It runs the container in the **background**. Your terminal is freed up immediately so you can type other commands. Without `-d`, the container runs in the "foreground", locking your terminal and printing logs directly to your screen until you press `Ctrl+C`. |
| `--name` | The Flag (Name) | Assigns a specific, human-readable name to this *running container*. If you omit this, Docker generates a random, funny name (e.g., `stoic_babbage`). Naming it makes it easy to reference later (e.g., when stopping it or viewing logs). |
| `test-honojs-app` | The Container Name | The actual name you are assigning to this specific running instance. |
| `-p 5000:5000` | The Flag (Publish/Port) | Short for `--publish`. It maps a port on your **Host** (your physical computer) to a port inside the **Container**. <br>**Format:** `HOST_PORT:CONTAINER_PORT`<br>**Meaning:** "Take traffic arriving at port 5000 on my Mac/Windows/Linux machine, and forward it to port 5000 inside the container." *(Note: The `EXPOSE 5000` in the Dockerfile is just documentation; `-p` is what actually opens the door).* |
| `test-honojs-app` | The Image Name | The name of the image you want to run. This must match the name you gave it during the `docker build -t` step. |

# 🌍 PART 3: Environment Variables

### `docker run -p 5000:5000 --env-file .env test-honojs-app`

| Component | What it is | Detailed Explanation |
| :--- | :--- | :--- |
| `--env-file .env` | The Flag (Env File) | Tells Docker to read a file named `.env` in your current directory and inject every `KEY=VALUE` pair inside it as environment variables into the container. This is much cleaner than typing them out one by one. |
| *(Alternative)* `-e KEY=value` | The Flag (Single Env) | Short for `--env`. Used to pass a **single** environment variable directly in the command. Example: `docker run -e PORT=8080 -p 8080:8080 my-app`. You can chain multiple `-e` flags together. |

# 🛠️ PART 4: Container Management Commands

### 1. `docker logs -f test-honojs-app`
| Component | Detailed Explanation |
| :--- | :--- |
| `logs` | Retrieves the standard output (stdout) and standard error (stderr) logs generated by the application running *inside* the container. |
| `-f` | Short for `--follow`. It acts like `tail -f` in Linux. Instead of printing the logs once and exiting, it **streams them in real-time**. You will see new logs appear on your screen the moment your app generates them. Press `Ctrl+C` to stop following the logs (this does *not* stop the container). |
| `test-honojs-app` | The name of the container you want to inspect. |

### 2. `docker stop test-honojs-app`
| Component | Detailed Explanation |
| :--- | :--- |
| `stop` | Gracefully shuts down a running container. It sends a `SIGTERM` (termination) signal to the main process inside the container, giving it 10 seconds to save data and close cleanly. If it doesn't close in 10 seconds, it sends a `SIGKILL` to force it to stop. |
| `test-honojs-app` | The name of the container to stop. |

### 3. `docker rm test-honojs-app`
| Component | Detailed Explanation |
| :--- | :--- |
| `rm` | Short for `remove`. It **deletes the container** from Docker's memory. <br>⚠️ **Important Rule:** You can only `rm` a container that is already **stopped**. If you try to remove a running container, Docker will throw an error (unless you force it with `docker rm -f`). |
| `test-honojs-app` | The name of the stopped container to delete. |

# ⛓️ PART 5: The Advanced Workflows (One-Liners)

Engineer 2 provided two powerful "one-liner" commands. Let's break down the magic behind them.

### Workflow A: The "Clean Rebuild" Chain
```bash
docker stop test-honojs-app && docker rm test-honojs-app && docker build -t test-honojs-app . && docker run -d --name test-honojs-app -p 5000:5000 test-honojs-app
```

**The Secret Sauce: `&&`**
In terminal/bash, `&&` means **"Logical AND"**. It tells the terminal: *"Run the next command **ONLY IF** the previous command succeeded (returned an exit code of 0)."* If any step fails, the chain stops immediately, preventing cascading errors.

**Step-by-Step Execution:**
1. `docker stop test-honojs-app` → Gracefully stops the currently running app.
2. `&& docker rm test-honojs-app` → Deletes the stopped container so the name is free to be used again.
3. `&& docker build -t test-honojs-app .` → Builds a brand new image with your latest code changes, overwriting the old image tag.
4. `&& docker run -d --name test-honojs-app -p 5000:5000 test-honojs-app` → Starts a fresh container using the newly built image.

### Workflow B: The "Ephemeral" (Temporary) Run
```bash
docker build -t test-honojs-app . && docker run --rm -p 5000:5000 test-honojs-app
```

**The Secret Sauce: `--rm`**
| Component | Detailed Explanation |
| :--- | :--- |
| `--rm` | Short for `--remove`. This flag tells Docker: *"When this container stops (either naturally or via `Ctrl+C`), **automatically delete it**."* |
| **Why use this?** | Notice there is **no `--name`** flag here. Because it auto-deletes, you don't have to worry about "name conflicts" (e.g., "container name already in use"). It also prevents your system from filling up with dozens of "Exited" containers over time. It is the absolute best practice for quick local testing. |
